# Findings — Skill vs. Species in AI Code Detection

Durable record as of 2026-05-20. Repo: `~/matthew/code-detection-confound`. All numbers are
script-emitted (see `results/analysis.json`, `results/format_ablation.json`,
`results/formatting_confound.json`, `results/droiddetect_validation.json`; macros in
`paper/macros.tex`). Paper prose: `paper/paper.tex` → `paper/paper.pdf`.

## TL;DR (the story arc)
Started as "do AI-code detectors detect author **skill** vs **species**?" The honest,
much sharper answer: **the strongest available trained detector (DroidDetect) is largely a
code-*formatting* classifier**, due to a **training-data collection artifact**. The skill
question is secondary (and the competitive-skill confound is absent).

## The data
- **cf set: 2844 samples** = 614 human (MatrixStudio Codeforces Python, accepted, difficulty
  bands easy≤1200 / hard≥1900) + 2041 LLM (gemma-2-2b-it, Qwen2.5-3B-Instruct, gpt-5.4-nano;
  natural/novice/expert prompts on the same problems).
- **legendary: 135** pre-LLM elite samples (Torvalds' initial git commit 2005, antirez Redis
  2012, Hipp SQLite 2013, CPython 3.3) — ironclad-human, contamination-free.
- **AtCoder: 54** human samples with real author Elo (low≤800 n=45 / high≥2000 n=9 — thin).
- Detectors: **DroidDetect-Base-Binary** (trained); **Fast-DetectGPT**, **Binoculars**
  (statistical, zero-shot). All vendored verbatim (`src/vendor/`); higher score = more AI.

## Finding 1 — DroidDetect is loaded correctly (control)
On the authors' OWN DroidCollection Python test data: **AUROC 0.999, human FPR 1.7%,
machine recall 98.3%** (`scripts/00_validate_droiddetect.py`). Reproduces the paper. So every
"bad" result below is real model behavior, NOT a loading bug. (We initially suspected a bug;
ruled out: verbatim TLModel class, strict load 0 missing/0 unexpected keys, encoder 134/134,
repo tokenizer ≡ base ModernBERT, projection_dim=256 read from weights — config.json's 128 is
stale, per-sample scoring since the mean-pool is unmasked.)

## Finding 2 — HEADLINE: DroidDetect classifies FORMATTING, not authorship
Semantics-preserving reformatting flips its verdict on its OWN human test data
(`scripts/08_format_ablation.py`, fig7). Fraction called MACHINE (argmax):

| corpus | original | black (comments KEPT) | ast.unparse (comments dropped) | comments-stripped only |
|---|---|---|---|---|
| DroidCollection-human (in-dist) | **0.010** | **0.828** | 0.525 | 0.030 |
| MatrixStudio-human | 0.705 | 0.965 | 0.855 | 0.760 |
| DroidCollection-machine | 0.985 | 0.977 | 0.863 | 0.975 |

- `black` (the standard formatter, **keeps comments/docstrings**, restyles only layout) flips
  in-distribution human code **1% → 83% machine**. Comment-stripping alone barely moves it
  (1%→3%). ⇒ the signal is **whitespace/layout**, not comments, not words.
- Identifiers preserved exactly (multiset mean = 1.000); strings/docstrings preserved. So this
  is NOT the legitimate "humans and AI use different words" signal.

## Finding 3 — WHY: a training-data formatting confound
`scripts/09_formatting_confound.py`. In DroidCollection's training distribution:
- Human Python: **15%** already black-compliant (mean similarity-to-black 0.837).
- Machine Python: **44%** already black-compliant (similarity 0.946).
Machine code is born clean (freshly generated by LLMs → canonical PEP8); human code is
scraped as-is. The detector learned "clean formatting = machine" — a collection artifact.
**Invalid at deployment**: real humans run formatters, so any black-formatted human code is
flagged. This is the root cause, and it generalizes the cross-source/legendary effects below.

## Finding 4 — Cross-source generalization failure (consequence of #3)
On MatrixStudio Codeforces human Python (a *different* scrape, tidier/low-comment), DroidDetect
flags **~62% (argmax) of ordinary human code** as machine — vs 1.7% in-distribution. Adding
gpt-5.4-nano to the panel dropped pooled cf AUROC from 0.83 (2-model) to **0.73**.

## Finding 5 — "Legendary pre-LLM coders" probe
At native argmax DroidDetect flags **78.5%** of provably-human pre-LLM elite code as AI
(CPython 97.5%, Hipp 72.5%, antirez 72.5%, Torvalds 60%). BUT ordinary MatrixStudio humans
are also ~62% → this is the formatting/cross-source effect, **not** a specific "elite code
flagged" effect. Use as illustration of the deployment risk, not as a skill claim.

## Finding 6 — The skill confound is ABSENT on the competitive axis
- Δ_confound (AUROC mismatched − matched) ≈ 0 for all detectors (DroidDetect +0.011,
  FastDetect −0.004, Binoculars +0.002).
- Within-species score slopes run AGAINST the naive skill prediction: DroidDetect human
  hard−easy = **−0.29** (CI excludes 0); LLM novice→expert −0.09. Higher competitive skill →
  scored slightly *less* AI. Competitive-programming style (terse) is the stylistic OPPOSITE
  of the idiomatic "senior-engineer" register RLHF models imitate.
- AtCoder real-author-Elo axis: high−low z negative/null (thin high band n=9, wide CIs) —
  same direction.
- Statistical detectors are weak on terse competitive code (pooled AUROC FastDetect 0.599,
  Binoculars 0.639) but **formatting-robust** (scores shift far less under reformatting) — the
  key between-family contrast.

## DroidDetect paper review (for Matthew's review of a similar paper)
Paper: Orel, Paul, Gurevych, Nakov, DroidCollection/DroidDetect, arXiv:2507.10583, EMNLP 2025.
**Verdict: not dishonest, but oversold via i.i.d.-only evaluation.**
- Headline F1 (99.2% binary) is an i.i.d. split (same generators/sources/preprocessing both
  sides; human & machine pools NOT problem-paired → invites source/format artifacts).
- They DO report cross-domain collapse (Table 3, ~45-pt F1 drop) and acknowledge limits — to
  their credit.
- Oversold in 3 concrete ways: (a) **NO fixed-FPR or calibration metrics anywhere** — a
  1.7%→62% FPR swing is invisible in weighted-F1/recall; (b) "strong cross-dataset robustness"
  (§D.2) shown only on GitHub-style corpora (The Heap, Swallow-Code), never a held-out
  Codeforces/algorithmic scrape; (c) the shipped checkpoint carries the i.i.d. headline
  numbers, inviting deployment §4.3 shows is unjustified. Their interpretability (§E.2:
  attention on punctuation/empty-lines/extra-spaces/comments) is consistent with our
  formatting-shortcut finding.
- **For the review, demand:** format-normalization ablation (does the signal survive `black`?);
  cross-source human held-out *within domain*; leave-one-generator-out; **fixed-FPR operating
  points + calibration (ECE/reliability)**; temporal split; per-source human FPR breakdown;
  report whether human/machine are problem-paired.

## Methodology decisions (vs initial_plans.html)
- Skill axis = problem difficulty (no public dataset joins human source to author Elo); AtCoder
  added as a real-author-rating confirmatory cohort.
- **AUROC** primary (not F1); **cluster bootstrap over problems**; within-species slopes are
  the mechanism test; Δ_confound per detector.
- DroidDetect reported at **native argmax** (its real operating point); statistical detectors at
  a fixed 5%-FPR point (they have no native threshold).
- Numbers flow script → `paper/macros.tex` (\res… `\newcommand`s) → hand-edited `paper.tex`;
  guard test `tests/test_paper_macros.py`.

## Finding 7 — The confound is FAMILY-WIDE, not a single checkpoint (scripts/10)
A web audit found NO clean out-of-the-box, standard-architecture AI-*code* detector on HF besides
the DroidDetect family (others are LoRA adapters / raw .pth / sklearn-joblib with undocumented
feature pipelines — running them would require the reimplementation we forbid). So we ran the
black-flip + legendary probe on all three published DroidDetect siblings (`results/other_detectors.json`):

| detector | DC-human orig → black | DC-machine | MS-human | legendary-all | CPython | Torvalds |
|---|---|---|---|---|---|---|
| Base-Binary (2-class, ModernBERT-base) | 0.013 → **0.831** | 0.987 | 0.713 | 0.830 | 0.975 | 0.600 |
| Base (4-class, ModernBERT-base) | 0.027 → **0.764** | 1.000 | 0.780 | 0.911 | 1.000 | 0.733 |
| Large-Binary (2-class, ModernBERT-large) | 0.007 → **0.811** | 0.980 | 0.700 | 0.763 | 0.975 | 0.467 |

- All three flip in-distribution human code from ~1% to ~80% "machine" under `black`. The confound
  is **architecture/size/granularity-invariant within the family** — consistent with a DATA cause
  (Finding 3), not a quirk of one checkpoint. **Scaling to Large does not fix it.**
- Legendary-flag and cross-source-FPR effects reproduce on every sibling (CPython ≥97.5% on all).
- CAVEAT on generality: same authors, same DroidCollection training data. To prove the confound
  lives in the DATA rather than the family's shared recipe, the decisive test is to fine-tune an
  INDEPENDENT architecture (RoBERTa/CodeBERT-ForSequenceClassification) on DroidCollection and run
  the same ablation. That is "train our own," a deviation from "use OOTB / never reimplement," so
  it needs explicit sign-off (proposed to Matthew).

## Findings 8–11 (2026-05-25 session, CodeGPTSensor reproduction + 2x2)

### Finding 8 — CodeGPTSensor in-distribution does NOT exhibit a formatting confound
Trained CodeGPTSensor (Xu et al., TOSEM 2025; UniXcoder-base-nine encoder, CE-only
fine-tune) on HMCorp Python (225k rows) and Java (152k rows) following their
published recipe (CGS pipeline imported verbatim from `external/CodeGPTSensor/`;
AMP-FP16, batch 8, lr 2e-5, seq 400, 20-ep cap, patience-5 ES on val_loss).

Reproduces paper Table 6 numbers:
- Python: F1 0.988, AUROC 0.999 (paper: F1 0.992, AUROC 0.999)
- Java:   F1 0.965, AUROC 0.995 (paper: F1 0.968, AUROC 0.995)

Formatting flip (test → test_formatted) on **machine class**:
- Python: machine-prob drops by +0.0007; TPR drops by +0.16 pp.
- Java:   machine-prob drops by +0.008;  TPR drops by +1.7 pp.

Pre-registered Q1 threshold was ≥ 0.10 on either metric. **Q1 = NO for both
languages on the pre-registered side.** Phase C (CodeGPTSensorBlack) skipped per
pre-registered decision tree.

`results/cgs/{python,java}_raw_ce/eval_phase_b.json`.

### Finding 9 — Length is not the discriminative signal
Pre-flight length-only logistic regression on HMCorp valid achieves AUROC
0.768 (Python) and 0.636 (Java) — both clear the < 0.80 "length not a sufficient
classifier" threshold from the pre-registered plan. Length-matched test slices
built (Python 17,380 / Java 17,000 rows, per-label BPE-length medians exactly
matched within 5%). Per-corpus AUC on length-matched slices stays ≥ 0.998
(Python) / 0.991 (Java). The model's discriminative signal is not length.

`results/phase_a/length_baseline.json`, `data/hmcorp/*/test_lenmatched*.jsonl`.

### Finding 10 — CodeGPTSensor catastrophically fails OOD on DroidCollection's distribution
Eval'd `python_raw_ce` on three OOD corpora:
- HMCorp test (in-distribution reproduction): AUC 0.999, FPR 1.1%.
- MatrixStudio Codeforces humans (n=614): flag rate 71.3% (humans flagged as
  machine). DroidDetect ref: 62%.
- Legendary pre-LLM Python humans (n=135, Sanfilippo/Hipp/CPython/Torvalds
  2005–2013): flag rate 26.7%. DroidDetect ref: 78.5%.
- DroidCollection test (n=23,405, mixed labels): **AUC 0.565** (near-chance).
  Human FPR 89.5%, machine TPR 96.6% — the model says "everything is machine."

Different shortcut from DroidDetect's — CGS doesn't latch onto formatting, but
latches onto *something* that doesn't transfer to DroidCollection. Hypothesis
(unconfirmed): "short docstring-completion style = machine," since gpt-3.5
HMCorp outputs structurally resemble Codeforces snippets.

In-distribution calibration is also poor: ECE 0.260 (correctly implemented
binary-classification ECE on confidence-in-chosen-class). The model is
overconfident.

`results/cgs/python_raw_ce/eval_phase_d.json`.

### Finding 11 — 2×2 architecture × data: BOTH matter, with data as the necessary condition
Trained UniXcoder-base on DroidCollection Python (114k rows balanced) using the
same CGS recipe (CE-only, AMP, batch 8, lr 2e-5, seq 400, 20-ep cap, patience-5
ES). Best F1 0.948 / AUC 0.989. Ran the formatting-flip eval.

**Pre-registration metric error discovered**: the Q1 trigger from the original
plan was on the MACHINE class (TPR drop / mean machine-prob drop). The canonical
DroidDetect formatting-confound symptom is on the HUMAN class (FPR increase
after black-formatting → "humans look like machines"). The two metrics agree for
severe confounds and clean cases; they diverge for moderate ones. Reporting both.

| Cell | Arch | Data | Human FPR shift |
|---|---|---|---|
| 1 Py | UniXcoder | HMCorp Python | -0.001 |
| 1 Ja | UniXcoder | HMCorp Java | +0.005 |
| 3 | UniXcoder | DroidCollection | **+0.210** |
| 4 (memory) | ModernBERT | DroidCollection | ~+0.82 |
| 2 (untested) | ModernBERT | HMCorp | — |

Interpretation:
- DroidCollection induces a formatting shortcut in BOTH tested architectures.
- HMCorp does not induce one in UniXcoder (Cell 2 with ModernBERT deferred).
- Architecture modulates severity ~4× on the same data (UniXcoder +21 pp vs
  ModernBERT +82 pp). UniXcoder's NL+PL pretraining provides partial robustness.
- The training-data per-label compliance gap does NOT predict severity: HMCorp
  has a +46 pp machine-vs-human black-near-compliance gap (vs DroidCollection's
  +27 pp), yet HMCorp induces no confound.

Story: data composition is **necessary** for the formatting shortcut to be
learned; architecture **modulates the magnitude**. Naive "the data is class-
imbalanced on formatting → the model learns formatting" is wrong as stated; the
gap doesn't determine severity, and one architecture (UniXcoder on HMCorp)
ignores even a +46-pp gap. Cell 2 (ModernBERT × HMCorp) would test the
remaining cell of the 2×2 but was deferred for compute budget.

`results/phase_e/cross_cell_q1.json`,
`results/phase_e/compliance_audit.json`.
