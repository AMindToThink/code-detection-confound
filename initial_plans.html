Does AI Code Detection Reduce to Skill Detection?

A pre-registered experiment to measure how much of an AI code detector's signal is explained by author skill rather than by author species.

Topic   Detection robustness Wall clock   24–48 hr autonomous Compute   local + existing credits

Motivation

Modern code-detection benchmarks treat human code as a single distribution and AI code as another. But humans vary enormously in skill, and post-RLHF code models are trained to imitate the upper tail of that human distribution. The reward models behind code-tuned LLMs are scored by senior engineers picking idiomatic, well-typed, well-documented code. If the LLM and the senior engineer have been pulled toward the same attractor in style-space, then "AI vs human" detectors may largely be learning "expert vs novice" instead.

This experiment tests that directly by measuring detector F1 inside skill-matched cells rather than on the full population. If detectors are species classifiers, their performance should hold up when humans and LLMs are matched on skill. If they are skill classifiers, performance should collapse on the matched diagonal and the headline F1 numbers reported in the literature are inflated by easy cross-skill comparisons.

Operational stakes
If the confound is real and large, the academic-integrity use case is structurally broken — detectors would penalize the strongest students alongside the cheaters, and miss weak students who prompt the model to write badly.

Hypotheses

Hspecies
Detectors are species classifiers. F1 is approximately constant across all (human-skill, LLM-style) cells. Skill-matched and skill-mismatched cells both achieve the headline F1 reported on standard benchmarks.
Hskill
Detectors are skill classifiers. F1 collapses toward random in skill-matched cells (high-skill humans vs naturally-prompted LLMs; low-skill humans vs novice-prompted LLMs) while remaining high in skill-mismatched cells. This is the pre-registered prediction.
Hmixed
Detectors learn a weighted combination of style and species cues. F1 degrades in skill-matched cells but not all the way to random. The degree of collapse quantifies the confound.
Hcond
Effect exists but varies with problem difficulty, language, or detector family.

Data Sources

Human code, stratified by skill

Primary source is the Codeforces public API. Each user has an Elo-style rating; each accepted submission carries the user's rating at submission time, the problem ID, the language, and the source text. Restrict to Python and C++ initially for coverage and tractability.

Sample roughly 100 problems uniformly across difficulty bands (problem rating 800 to 2800). The cross-product gives ~10,000 human samples with known author rating, problem ID, problem difficulty, and language.

LLM code on the same problems

For every problem in the human set, generate solutions with a panel of models. Prompt minimally with the problem statement and no skill conditioning. Use each model's recommended default sampling parameters from its system card or release documentation, with n = 5 samples per (problem, model). Filter to accepted solutions only, since Codeforces only exposes accepted submissions on the human side.

  • Frontier RLHF   GPT-4o, Claude Sonnet 4.6, Gemini 2.5 Pro
  • Code-specialized   DeepSeek-Coder-V3, Qwen2.5-Coder-32B
  • Smaller / open   Llama-3.1-8B-Instruct, CodeLlama-7B

The novice-prompted condition

Generate a second LLM set with explicit novice-style prompting, holding model and problem fixed.

  • novice_prompt   "Solve this using only basic constructs. No type hints, single-letter variables where natural, minimal comments. Write like a beginner who is still learning the language."

This is the critical condition. If detectors are skill classifiers, novice_prompt LLM output should look like low-skill human code and detector F1 against low-skill humans should collapse. An expert_prompt condition is omitted from the main analysis on the prior assumption that naturally-prompted RLHF'd LLMs are already at the senior-engineer attractor, so an explicit expert prompt would produce a distribution indistinguishable from natural. Worth a quick sanity check at the end but not load-bearing.

The family split matters for interpreting the results. Trained detectors learn whatever discriminates AI from human in their training data; if that data is recent (DroidCollection was released in 2025), the decision boundary is calibrated to modern post-RLHF LLM output, which means the senior-engineer attractor sits squarely inside the "AI" region of the learned space. Statistical detectors instead query a base LLM about how surprised it would be by the code, which is a different mechanism that may or may not pick up the same confound.

NanoDroid is the detector from the paper under review and is not used here. The paper is anonymous and under double-blind review, so even a public repo (if one exists) should not be searched out, since doing so risks deanonymizing the authors.

For each detector, store the raw pre-threshold logit, not the binarized label. This lets the analysis use a continuous response and allows threshold tuning per cell.

Analysis

Primary analysis  ⋄  skill-stratified F1

Build a 5×2 grid of evaluation cells. Rows are human rating bands (newbie, pupil, expert, candidate master, master+). Columns are LLM prompting conditions (natural, novice). Each cell contains the human samples from that rating band and the LLM samples generated under that condition.

For each (detector, language, cell) triple, evaluate binary classification F1. The headline output is a 5×2 heatmap of F1 per detector. The two diagnostic comparisons are:

  • Skill-matched cells.   High-rated humans vs naturally-prompted LLMs (top-right). Low-rated humans vs novice-prompted LLMs (bottom-left). Under Hskill, F1 collapses toward 0.5 here.
  • Skill-mismatched cells.   Low-rated humans vs natural LLMs (bottom-right). High-rated humans vs novice LLMs (top-left). Under both Hspecies and Hskill, F1 stays high.

The headline statistic is the F1 gap between mismatched and matched cells, averaged across detectors.

Δconfound  =  F1mismatched  −  F1matched

A large positive Δ is direct evidence that the detector's apparent performance on standard benchmarks is propped up by easy cross-skill comparisons. A Δ near zero means the detector is genuinely doing species classification.

Secondary analysis  ⋄  continuous regression

For each (detector, language) cell, fit a mixed-effects model on human-only data to get a continuous view.

logit P(AI)i  =  α  +  β · ratingi  +  γ · difficultyp(i)  +  up(i)  +  εi

where up is a per-problem random intercept. Report β in units of logit-P(AI) per 400 rating points (one Elo tier), with bootstrap 95% CI over resampled problems. This complements the F1 cells with a continuous gradient and reveals whether the skill axis is smooth or discrete.

Robustness checks

  • Per-problem F1.   Restrict each F1 cell to problems where both rating-band humans and the relevant LLM condition produced accepted solutions. Removes the obvious confound that high-rated users tend to attempt harder problems.
  • Monotonicity.   Isotonic regression of P(AI) on rating. Test the null of flat fit versus monotone fit via likelihood ratio.
  • Calibration.   Per-tier accuracy plot. If accuracy degrades monotonically with rating, this is direct evidence of the confound at the operating point.
  • Geometric view.   Penultimate-layer embeddings of all samples, UMAP'd. Color by (a) class label, (b) rating, (c) language. If the rating gradient aligns with the AI vs human axis, the confound is visible in the representation, not just at the output.
  • Optional sanity check.   Generate a small expert_prompt set and verify that its detector logits are statistically indistinguishable from the natural-prompt LLM set. If they differ, the "natural is already at the senior attractor" assumption fails and the design needs revision.

Predictions

⤧   If Hskill holds
  • F1 in skill-matched cells collapses to < 0.65 on at least 4 of 6 detectors
  • F1 in skill-mismatched cells stays at the published headline level (≥ 0.90)
  • Δconfound ≥ 0.20 averaged across detectors
  • Master-tier humans misclassified as AI in ≥ 25% of cases when compared against natural-prompt LLMs
  • Novice-prompted LLMs misclassified as human in ≥ 25% of cases when compared against newbie humans
  • Regression slope β: substantial and positive, with logit-P(AI) shifting by ≥ 0.5 across the rating range
○   If Hspecies holds
  • F1 approximately constant across all 5×2 cells
  • Δconfound < 0.05
  • Novice prompts do not meaningfully shift detector logits on LLM output
  • Regression β near zero, slopes flat across rating bands

Hmixed is the most likely outcome in practice. Some confound, but not total collapse. The headline number then becomes Δconfound, which quantifies how much of the reported F1 is "free" cross-skill signal. The reason to pre-register thresholds is that any of the three outcomes is publishable. A clean Hskill result reframes the field; a clean Hspecies result strengthens the deployment case for current detectors; Hmixed with a quantified Δ is the most likely scientific contribution.

Between-family prediction
Trained detectors should exhibit substantially larger Δconfound than statistical detectors. Supervised models learn the decision boundary that best separates their training distribution, and if that training data is recent enough to include modern post-RLHF code, "AI" effectively means "senior-engineer attractor" in the learned representation. Statistical detectors measure log-probability curvature under a base LLM, which is a different signal — possibly correlated with skill, but not directly trained against a recent AI-vs-human label. The expected ordering is Pangram ≈ DroidDetect ≈ UniXcoder > GPT-Sniffer > Binoculars ≈ Fast-DetectGPT, with the trained-vs-statistical gap as the key diagnostic.

Implementation Plan

Hr 0–4
Data collection. Pull Codeforces problems and submissions via the public API. Stratified sample across rating bands and problem difficulties. Store source, rating-at-submission, problem ID, language. Deduplicate near-duplicate solutions within users. Mostly rate-limit-bound.
Hr 4–16
LLM generation. Submit each problem to each model under natural and novice conditions, n = 5 each, using model-default sampling. Parallelize across providers. Validate accepted solutions either via the Codeforces submission interface or a local judge. Most wall-clock is API rate limit waiting.
Hr 16–28
Detector preparation. Train DroidDetect-CLS Base, UniXcoder-FT, GPT-Sniffer-FT on DroidCollection per their published protocols. Run two in parallel across the 2×RTX8000. Wire up Pangram API, Fast-DetectGPT, and Binoculars.
Hr 28–32
Inference. Run every sample through every detector. Store raw logits.
Hr 32–44
Analysis and write-up. 5×2 F1 heatmaps per detector. Mixed-effects regression. Calibration plots. UMAP embeddings. Threats to validity. Final report.

The whole pipeline fits inside ~48 hours of wall-clock for an autonomous agent. The bottleneck is API rate limits on the LLM generation step, not compute or analysis. Fire and forget.

Threats to Validity

  • Self-selection. Codeforces users are not a random sample of programmers. Replicate on a second source (LeetCode contests, AtCoder, or stratified GitHub by maintainer reputation) if time permits.
  • Rating as a proxy for skill. Competitive-programming rating measures one specific skill (algorithmic problem solving under time pressure) that may not map cleanly to "writes idiomatic production code." This is a known limitation; document it rather than fight it.
  • Filtering bias. Restricting to accepted solutions biases toward correct code on both sides. Plausibly this understates the confound, since incorrect human solutions would presumably be even less polished.
  • Detector contamination. If DroidCollection's "Human" class contains Codeforces submissions, the detectors may have seen the test data during training. Check overlap by problem ID and timestamp.
  • Model snapshot drift. Frontier-model behavior changes across versions. Lock model identifiers and dates in the released artifact.

Fallbacks

Things that are likely to go wrong, and what to do about them. Claude Code should attempt the happy path first and degrade gracefully through these in order.

Codeforces data collection

  • If the Codeforces API rate-limits aggressively (the documented limit is ~1 request per 2 seconds on some endpoints), use a pre-scraped Codeforces dataset from HuggingFace such as open-r1/codeforces, MatrixStudio/Codeforces-Python-Submissions, or similar. Pay the cost of working with a snapshot.
  • If submission source-code scraping is impractical (the source is on the website, not the API), AtCoder has a similar Elo system and exposes submission source directly via its public API. Acceptable substitute.
  • If both fail, fall back to the existing DroidCollection competitive-programming partition for the human side. Lose the rating-stratification metadata, but in that case pivot to using contributor reputation on OSS code (GitHub stars, contribution count) as a coarse skill proxy.

LLM generation

  • If API rate limits or token credits get tight, drop sample count from n = 5 to n = 2 and restrict the model panel to the three frontier RLHF models plus DeepSeek-Coder. Five models is enough to characterize the LLM side.
  • If a model refuses some competitive problems (unlikely but possible for problems with sensitive flavor text), document the refusal rate and proceed with what remains.
  • If LLM-side acceptance filtering via the Codeforces submission interface is impractical, evaluate on the CodeContests test cases for problems that have them, or skip acceptance filtering entirely and note that LLM-side data includes failed solutions. The matched-problem property is what matters; acceptance is a nicety.
  • If everything fails, use a pre-existing LLM-on-Codeforces dataset such as LiveCodeBench or CodeElo generations. Lose the controlled prompt conditions, gain a working pipeline.

Detector training

  • DroidCollection is ~847k training samples. If full training does not fit in the 48-hour budget on 2×RTX8000, reduce to 1 epoch (the paper trains 3) and batch size 32. The detection task is easy enough that 1 epoch usually gets within 1-2 F1 of full training.
  • If retraining from scratch is too slow, use the publicly-released DroidDetect checkpoint from HuggingFace (Orel et al. 2025b is on the hub) and any UniXcoder/CodeBERT detection checkpoints that exist. Note in the writeup that these are vendor checkpoints, not retrained.
  • If GPU memory is a constraint, LoRA-tune the backbones (r = 16) instead of full fine-tuning. Should preserve the decision boundary while reducing memory by ~5×.
  • If training fails entirely, drop to the four detectors that don't need it (Pangram, Fast-DetectGPT, Binoculars, plus DroidDetect checkpoint). Smaller panel, still tells the same story.

Detector contamination

  • The DroidCollection training set includes competitive-programming code. Before any analysis, check problem-ID overlap between the test problems sampled here and DroidCollection's training partition. If overlap is large, restrict the test set to problems from contests held after DroidCollection's data cutoff (the paper documents the cutoff).
  • Report all results both with and without overlap removal. The contamination-free numbers are the load-bearing ones.

Statistical power

  • If accepted-solution filtering leaves cells with fewer than 50 samples, relax the human filter to include solutions within one rating tier of the band's edge.
  • If Pangram API is over budget, run it on a stratified subsample (20% per cell). Statistical detectors are free, so they always run on the full set.
  • If any cell remains undersampled, report bootstrap CIs explicitly and flag the cell in the heatmap.

Minimum publishable result

If multiple failures cascade, the minimum result that still answers the central question is: at least two detectors (one trained, one statistical), at least two LLM conditions (natural, novice), at least two human rating bands (low and high), evaluated on at least 30 problems with matched coverage. This is sufficient to compute Δconfound for one trained and one statistical detector, which is enough to make the between-family claim. Everything above this floor is a nice-to-have.

Deliverables

  • A public dataset of (problem, rating, language, source, detector logits) tuples
  • A reproducibility script that goes from raw API pulls to the headline plot in under an hour on a single A100
  • A short paper or technical report with the regression table, the calibration plots, and the embedding visualizations
  • If results support H₁, a proposed evaluation protocol for future detector papers requiring skill-stratified reporting
